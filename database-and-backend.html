The ideas the design rests on

  • A person sells, the app records. The public form saves a lead; a SuperAdmin calls, agrees the deal and creates the customer. There is no self-serve signup, payment or card.
  • Nothing ever locks. Trial ended, Suspended, Cancelled and Overdue are labels. A customer is never locked out of login, data or any mobile feature because of a status or an unpaid invoice.
  • No agreement row = existing customer. Every current company keeps working with every feature on and nothing billed, so no backfill and no migration of live data is needed.
  • Xero holds the real invoice. The app creates a Draft in Xero; a person approves and sends it there. The app never emails an invoice, stores a PDF or takes a payment.
  • Everything is idempotent. A unique key per invoice and guarded status updates mean converting twice, clicking twice or re-running the nightly job never duplicates anything.
  • Hand-run SQL, no database foreign keys. Six new tables, created by a script the owner runs; links between tables are logical (matching ids), like the rest of this database.
  • Fail open. If the feature lookup, Xero or the database hiccups, customers keep working and the problem is logged and shown to the SuperAdmin.

Conventions every table follows

  • Id NVARCHAR(50) primary key, generated by the app (sequential GUID text) — never set by hand.
  • CompanyId NVARCHAR(50) for tenant scoping (never MAX: a MAX column cannot be indexed). Company.Id and the existing tables that hold it are matched by value, not by constraint.
  • User ids are NVARCHAR(450) (the width of AspNetUsers.Id).
  • Standard audit columns on every table: IsDeleted, CreatedAtUtc, CreatedById, UpdatedAtUtc, UpdatedById.
  • Soft delete. There is no global filter: every query adds IsDeleted = 0, and unique indexes are filtered with WHERE IsDeleted = 0 so a deleted row never blocks a new one.
  • Enums are stored as text ('Trial', 'PerGuard'), not numbers, so raw SQL stays readable. The set of allowed values is checked in code, not by a database constraint.
  • Money is DECIMAL(18,2) in AUD, ex-GST. Dates and times are UTC.
  • Created by a hand-run script (sql/CustomerAgreements.sql), not by the app on startup. Entity classes live in Demo/Entities (namespace Domain.Entities) and each gets an EF configuration extending BaseEntityConfiguration<T>.

The $99 monthly minimum applies per account (10 guards on Starter is $60 of usage, billed as $99). An annual licence is prepaid at 10 months for 12 and is sized by the included guards band, not by usage. A negotiated annual amount overrides the formula and needs a reason, which is written to history.

Rules

  • PerGuard: monthly = max(MinimumMonthlyCharge, guards × rate); billed in arrears for the month just ended, using that month's guards scheduled.
  • AnnualLicence: annual = max(min, includedGuards × rate) × 10, or the negotiated override. Billed once, ahead.
  • Custom: annual is entered by hand; there is no formula.
  • Invoice line total = round(qty × unit, 2); subtotal = sum of line totals; GST = round(subtotal × 10%, 2) once on the subtotal (never per line); total = subtotal + GST. Rounding is half-up (away from zero) to the cent. If the customer is not charged GST, GST is 0.
  • ABN is required before an invoice goes to Xero when the total is $1,000 or more (accountant to confirm the rule and threshold).

Proposed C#

// Application/Common/Services/CompanyAgreement/InvoiceMath.cs   (pure, decimal — never double)
public static class InvoiceMath
{
    public static decimal Round2(decimal v) => Math.Round(v, 2, MidpointRounding.AwayFromZero);

    public static InvoiceTotals Total(IEnumerable<InvoiceLine> lines, bool chargeGst, decimal gstRatePercent)
    {
        var subtotal = Round2(lines.Sum(l => Round2(l.Qty * l.UnitPrice)));
        var gst = chargeGst ? Round2(subtotal * gstRatePercent / 100m) : 0m;   // once, on the subtotal
        return new InvoiceTotals(subtotal, gst, Round2(subtotal + gst));
    }
}

// PerGuard      -> guards = ScheduledGuards; listMonthly = max(min, guards * rate); annual = listMonthly * 12

The app prepares and mirrors; Xero holds the invoice. Everything goes in as a Draft that a person approves in Xero.

Platform connection

  • Engage WorkForce's own Xero organisation is connected once by a SuperAdmin through four dedicated actions. The existing tenant Xero code (OAuth handlers, token provider, contact and invoice calls) is reused with a reserved company id.

7Nightly job

CompanyAgreementLifecycleService runs at 05:00 UTC through Hangfire, and on demand through Run now (the Hangfire server is deliberately off on developer machines, so this is how it is exercised locally).

// Program.cs — PROPOSED, mirrors the existing daily-billing-run registration
if (runHangfireServer)
{
    RecurringJob.AddOrUpdate<ICompanyAgreementLifecycleJob>(
        "company-agreement-lifecycle",
        j => j.RunAsync(CancellationToken.None),
        "0 5 * * *",
        new RecurringJobOptions { TimeZone = TimeZoneInfo.Utc });
}

1 · Trial pass

  1. Expire trials: UPDATE CompanyAgreement SET Status='TrialEnded' WHERE Status='Trial' AND TrialEndsOn < @Today (guarded), then a history line and the 'Trial ended, follow up now' email — once, via TrialEndedNotifiedAtUtc.
  2. Remind: trials ending in 3 days / 1 day go into the digest, once each (ReminderDay3SentAtUtc, ReminderDay1SentAtUtc). Dates are compared by day, so a re-run never double-sends. Customer-facing reminders are off by default (NotifyCustomerOnReminders).
  3. Feature overrides expiring within 3 days are listed in the digest.

2 · Billing pass

  1. Retry every Queued invoice that has a BlockedReason (the billing details may be complete now, or Xero is back).
  2. Read back every open invoice from Xero (one batched call) and mirror its status.
  3. Create the Monthly and Renewal invoices that are due. The unique key makes this idempotent; a cancelled invoice keeps its key, so it is not recreated.
  4. Note newly overdue invoices (once, then every 7 days until paid). Xero sends its own customer reminders.
  5. One digest line if Xero needs reconnecting, with the number of invoices waiting.
Everything is idempotent: re-running the same night sends and creates nothing new. The billing pass never changes CompanyAgreement.Status; only the single guarded Trial → TrialEnded flip does.

13Gaps found while writing this

Found while writing this. All six are now decided and in the plan (decisions 21 to 26).

Decided: a crash between Xero and our database could create a duplicate Draft.
CreateInvoiceInXero calls Xero first and only then stores XeroInvoiceId; a crash in between would leave a Draft we do not know about. Fix: every invoice carries EWF-{Kind}-{PeriodKey} in the Xero Reference (after any PO, no internal ids, because it prints on the invoice), and CreateInvoiceInXero looks it up on the contact before creating. See the CreateInvoiceInXero operation.
Decided: a Draft deleted inside Xero goes back to Queued.
Sync maps DELETED → Queued (Xero id cleared, recreated the next night) and SUBMITTED → Draft; anything else unknown keeps the old status and logs a warning. Deleting in Xero does not stop a charge: use Cancel in the app.
Decided: a customer can be created without its agreement.
ProvisionAsync commits before the agreement is written and cannot be rolled back. The activation link is now sent only after the agreement saves; a failure returns a warning with Attach agreement, and the Customers page flags the company as Agreement missing. See CreateCustomerAccount.
Decided: end dates are whole days.
TrialEndsOn, RenewalOn and ExpiresOn are DATE columns holding the last day included, compared with today's UTC date, so "until 30 Nov" works all of 30 Nov. For AU / NZ customers the UTC day ends a few hours after their midnight, so a date lasts slightly longer than promised, never shorter.
Decided: guard counts use the site's own month.
Shift times are the site's local time, so the count compares them with plain month dates and never converts to UTC; month edges are then exact. An overnight shift counts in the month it starts. The per-guard billing day defaults to the 2nd, so customers west of UTC (still on the last evening of the month when the job runs on the 1st) are not missed.
Decided: the feature cache stays per server.
Instant on today's single IIS site. If the app ever runs on two or more servers, a change can take up to 5 minutes to reach the others; the upgrade is to move the cache onto the existing ICacheService with Redis. Nothing to build now.
